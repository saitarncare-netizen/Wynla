## Where the data comes from

1. **Research + verification workflow (2026-09-23).** Four rosters were read from the official sites only (epicpass.com, news.vailresorts.com, ikonpass.com, alterramtn.co, indyskipass.com, mountaincollective.com, plus resort-operated pass pages), then a second pass verified every row and applied corrections. Outputs live in the handoff folder `ridewise-handoff/pass-data-2026-09-23/`:
   - `resort_pass_access.json` — 1,115 rows (slug, pass_family, product, days, blackout_dates, reservation_required, source_url, verified_on, plus `bonus_mountain`, `group_id` / `shared_allotment`, `partner_kind`, `notes`, `new_for_2026_27`).
   - `rosters-verified.json` — per-family products with prices, deadlines and caveats, and per-resort access.
   - `CHANGES.md` — the narrative and the per-slug tag diff that was applied to `resorts.passes[]`.
2. **`node scripts/build-pass-access.mjs [input]`** turns that file into `lib/data/passAccess.json`:
   - drops the 141 rows whose roster resort has no `resorts` row (`slug: null`) and the 14 `Indy XC Pass` rows (a nordic-only product Wynla does not sell or filter by). Alpine products at the one nordic partner that has a DB row (`quarry-road-trails`) are kept, so a resort the DB tags `indy` never shows an empty card;
   - normalises product names to one canonical name + stable key (`Indy Base AddOn Pass` → `Indy Base Add-On Pass` / `indy-base-add-on-pass`), splitting tier or age qualifiers (`Epic Day Pass - All / 32 / 22 Resorts tiers`, `Park City Youth Pass (child 5-12)`). An unknown product name throws, so a new roster cannot slip through untyped;
   - parses `days` into `{kind, count|min|max, short, qualifier}`; `2 (Bonus Mountain)` → 2 days, "full Ikon Pass only"; `7` at Killington/Pico → "shared across Killington and Pico" (from `group_id`);
   - parses `blackout_dates` into ISO ranges for 2026-27 when the text spells dates out. Year-less tokens go to 2026 for Jul-Dec and 2027 for Jan-Jun. A bare "peak dates" (three Epic regional products) is expanded to the published Epic peak list and marked `rangesSource: "epic-peak-list"`. Epic Day Pass rows are `conditional` (peak dates only on the no-peak option). Indy rows that say "26/27 dates TBA" are `unpublished`, with last season's list turned into plain words for the hint. Products with no access are `not_applicable`. The raw text is kept on every row;
   - sorts by slug, family (MC, Ikon, Epic, Indy) and product display order.
3. The app imports the JSON at build time. There is no runtime fetch and no DB read for pass rules.

## What the UI promises (and does not)

- `isBlackedOut` answers `true` / `false` only from explicit ranges or weekday rules. It returns `null` for unpublished lists, option-dependent products, no-access products, unknown products and invalid dates. Callers render `null` as "not announced yet", never as "open".
- Indy Base Pass rows that show "No blackout dates" mean the resort's Indy page carried no blackout badge on 2026-09-23. Indy publishes the 2026-27 list in fall 2026; the family note on the card says so.
- Bonus mountains: the row says "2 days · full Ikon Pass only", the card carries the yellow "Bonus mountain: 2 days on the full Ikon Pass only. Not on Ikon Base or Ikon Session." line, and the Base / Session rows say "Not included".

## Founder decision on Ikon Bonus Mountains

Ten US Bonus Mountains (buck-hill, caberfae-peaks, devils-head, giants-ridge, jiminy-peak, ski-butternut, snowy-range, tamarack, wild-mountain; Cranmore NH has no DB row) stay tagged `ikon` in `resorts.passes[]`, so they keep the Ikon colour on the map and match the pass filter. The tier distinction (2 days, full Ikon Pass only, blackouts apply even on the full pass) is carried by `isBonusMountain` in the dataset and shown on the resort page and in the chip summary. No `ikon_bonus` value is introduced: the map filter answers "can my Ikon get me on this hill" (yes, on the full pass), and the detail answers "for how long". Revisit only if users report being misled by the colour.

## Weekly re-verification in selling season (15 minutes)

Do this every Monday from October to the first week of December, and once when Indy publishes blackouts. Open each page as a normal browser visit (epicpass.com sits behind a Queue-it waiting room that blocks scripted fetches).

| Min | Check | URL | What to look for |
|---|---|---|---|

| 3-6 | Epic products | https://www.epicpass.com/passes/epic-pass.aspx · https://www.epicpass.com/passes/epic-local-pass.aspx · https://www.epicpass.com/info/peak-restricted-dates.aspx · https://www.epicpass.com/passes/northeast-value-pass.aspx | Peak-date list unchanged; Epic Local 10-day trio (Vail, Beaver Creek, Whistler) and "unlimited excluding peak" five (Park City, Heavenly, Northstar, Kirkwood, Stowe); Telluride 7-day rule on https://tellurideskiresort.com/epic/. |
| 6-10 | Indy blackouts + roster | https://www.indyskipass.com/blackout-dates-reservations · https://www.indyskipass.com/our-resorts | **Until the 2026-27 list is published, nothing to change.** When it is: copy each resort's dates into `blackout_dates` in the handoff JSON (format `Dec 20 2026 - Jan 4 2027, Jan 16-18 2027`), remove the "26/27 dates TBA" prefix, regenerate. Also scan for new partner cards and removed ones. |
| 10-12 | Mountain Collective | https://mountaincollective.com/resorts/ · https://mountaincollective.com/reservations/ | 13 US destinations; Jackson Hole reservation requirement; Big Sky reservations (a third-party source claimed one — verify in November). |
| 12-14 | Regenerate + test | `node scripts/build-pass-access.mjs` then `npm test` | The stats line must still match `resorts.passes[]` counts (or the DB change goes in the same PR). Diff `lib/data/passAccess.json`; unexpected changes mean a parse regression. |
| 14-15 | Bump the stamp | `verified_on` in the handoff JSON (the script copies it) | Every card prints "Verified <date>", so the date must move when the check happens, even when nothing changed. |

If a resort joins or leaves a family, `resorts.passes[]` must change in the same batch (read-only PostgREST check: `select=slug,passes&passes=cs.{ikon}`), because the resort page only renders cards for families in `passes[]`.
